# 无人值守实验编排

**IRON LAW：实验一旦开跑，Claude 就下线。** 运行期间的一切“盯着看”都交给看门狗脚本；Claude 不轮询、不定时唤醒自己查看、不派子代理盯作业、不中途改代码重部署。Claude 只在两段工作：**开跑前**（配环境、debug、最小冒烟测试证明代码能跑、确认要落盘的东西会落盘）和**收尾后**（用户明确说“可以写了”才按约定规格出报告）。

Red Flags（出现任何一条，停下回到对应步骤）：
- 想设一个定时器“过一会儿看看作业” → 这是看门狗的活，回第 6 步补看门狗
- 冒烟测试在等预热、等窗口、测好几档 → 那是在模拟正式实验，回第 4 步
- 估算发现跑完要几天甚至几周，却打算“先跑起来再说” → 回第 2 步重新设计规模
- 作业在跑时想改测量代码并重新部署 → 停：要么等这一批结束，要么按第 9 步“中途改条件”走
- 看到异常数字先猜原因就改协议 → 回第 1 步先查根因

## 分工

| 角色 | 负责 | 不负责 |
|---|---|---|
| 用户（负责人） | 研究问题、固定条件、验收标准、预算；运行中改条件的决定；何时写报告 | 具体脚本 |
| Claude | 环境、依赖、debug、最小冒烟测试、编排器和看门狗、提交前的说明、收尾报告 | 运行期间的监控和干预 |
| 编排器（脚本） | 把矩阵一次性提交给调度器；每个独立系列一个作业；落盘元数据 | 判断数据好坏 |
| 看门狗（脚本） | 检测卡死/崩溃/可疑数据，写状态板和 ALERT，有限次自动续提，清理现场 | 修 bug、改协议 |
| 调度器（Slurm 等） | 按配额排队，“尽可能并行”由它实现 | — |

### 0. 对齐目标与边界 ⚠️ REQUIRED

只问真正缺的。要回答这些问题：
- 实验矩阵是什么？每个维度有哪些取值（模型×数据集×硬件×超参……）？哪些组合必须做，哪些可以缺测？
- 哪些条件是固定的（用户原话里写死的）？哪些是 Claude 可以自己定的？
- 每个点“有效”的标准是什么（最少样本/轮次、最长时长、何时判为可疑）？
- 什么情况停测（OOM、容量不足、连续失败）？停了之后更高档位怎么处理？
- 账号的资源配额是多少（同时多少卡、作业最长多久）？结果要推到哪里？
- 报告和仓库有没有现成规格（如 create-research-experiment-repo）？有就照用，没有才自己写。

用户说“规格你自己定”时，把定下的规格写成文件（设计文档），后面所有判断都以它为准。

### 1. 异常先查根因 ⛔ BLOCKING（有异常时）

接手前人项目或看到离谱数字（耗时比预期长十倍、token 数异常、吞吐忽高忽低）时，**先诊断再改协议**：
- 用已有的原始记录做离线分析（分布、尾部、失败样本长什么样）。
- 设计一个小的对照实验，每次只换一个变量，用置信区间判断差异。
- 查外部资料（官方文档、issue、论文）确认是否已知问题。
- 结论和数据写进诊断文档，再据此改协议，并在设计文档里记录“改了什么、为什么”。

### 2. 可行性预算 ⚠️ REQUIRED

估算：单个数据点耗时 × 每点数据点数 × 点数 ÷ 可并行的槽位数。回答：
- 总时长能不能接受？单个点能不能在用户能接受的时间内出结果？
- 如果不能，能否改成“抽样/稳态窗口”而不是“跑全量”，同时用最少轮次、置信区间保证结果可信？
- 每个点设硬上限（时间和规模），到上限还不达标就标“可疑”，不无限延长。

把估算写给用户看，不要“先跑起来再说”。

### 3. 环境与 debug

在计算节点上（不是登录节点）准备运行环境，所有路径、版本、模型/数据的哈希写进一个 env 文件和元数据。测量逻辑写成可单测的模块，本地先跑单元测试（用假的服务器/假的任务）。

### 4. 最小冒烟测试 ⚠️ REQUIRED

**目的只有一个：证明流程能跑通、记录能落盘。不是小规模正式实验。**
- 只测一个最小档位，不预热、不开测量窗口，第一个数据点完成就停。
- 多轮交互类任务挑一个已知简单的样本放最前面，缩短单个数据点耗时。
- 跑完逐项检查：作业日志、运行元数据（配置/版本/源码提交）、事件记录、指标时序、单点汇总都在；临时文件和容器已清理；`scancel` 后能正常走清理流程。
- 冒烟产出的数字一律不进报告。

### 5. 编排器

载入 [references/orchestration-patterns.md](references/orchestration-patterns.md) 按模板写。要点：
- 一个“系列”（同一硬件×同一任务，按档位递增）一个作业；服务只启动一次，档位依次测。
- 用一个脚本一次性提交全部系列，超出配额的由调度器排队，不自己写排队逻辑。
- 每个作业落盘：`run.json`（配置、源码提交、版本、硬件身份）、心跳文件、事件日志、指标时序、每个点的汇总、系列状态日志。
- 停测规则写进作业脚本（容量失败 → 更高档位标“未测”）。
- 参数通过文件传，不通过逗号分隔的环境变量传 JSON。
- 部署脚本给集群上的代码打上源码提交号；工作区和提交不一致时标 `+dirty`。

### 6. 看门狗 ⚠️ REQUIRED

载入 [references/watchdog-design.md](references/watchdog-design.md)。两层：
- **作业内看门狗**：服务进程是否活着、指标是否还在动、是否长时间没有数据点完成；卡死时优雅终止当前点（让任务进程清理自己的容器）。
- **矩阵看门狗**：独立的 CPU 作业（不是 Claude、不是用户的笔记本），维护状态板和 ALERT 日志；作业异常消失时有限次自动续提；为结束的作业提交同节点清理；全部结束写 DONE。

可疑数据的判定规则在开跑前定死，由看门狗打标记，不靠事后人工挑。

### 7. 开跑前确认 ⛔ BLOCKING

给用户一页说明，然后等明确的“开跑”：
- 矩阵和固定条件（标出和用户原始要求不同的地方及理由）
- 预计总时长、占用多少卡、什么时候能出第一个结果
- 停测规则和可疑判定
- 冒烟测试结果（只说流程通了，不报数字）
- 查看状态的命令（例如 `status.sh <矩阵名>`）

### 8. 提交并下线

运行提交脚本，记录作业号、状态板位置，告诉用户怎么看状态。**然后结束本轮工作，不设定时唤醒、不轮询。** 如果有长时间的后台传输（下载、镜像中转），也要放进调度器作业或用户可见的终端，不要挂在 Claude 会话的后台进程里——会话一断它就停。

### 9. （条件）运行中用户改条件

用户在运行中改了固定条件（例如关掉某个加速选项、换采样参数）：
1. 停掉受影响的作业（不影响的继续跑）。
2. 在设计文档里记录新决定、时间和理由，标明哪些已有数据作废（原始记录保留，不进结论）。
3. 改代码 → 本地测试 → 部署 → **重新做最小冒烟** → 重新提交。
4. 只在作业之间部署；正在跑的作业会在下一个点读到新代码，可能导致同一系列前后不一致。

### 10. 收尾：按指示写报告

用户明确要求时才做：
- 先汇总所有点的汇总文件，检查可疑标记和 ALERT。
- **可疑数据立即告诉用户**，派子代理查根因，子代理必须交证据链（原始日志、指标时序、轨迹片段、复现命令），主代理逐条核实后才采纳；核实前可疑点不进结论曲线。
- 按事先约定的报告规格写；规格以外的发现另起一节。

## 反模式

- 用 ScheduleWakeup/cron/子代理轮询当监控 → 看门狗脚本做
- 冒烟测试测多个档位、带预热和窗口
- 每个数据点都要人工/AI 审批、逐任务重算回执，流程本身成了瓶颈
- “每个点跑完整数据集”，不估算就开跑
- 指标定义没想清楚就用（例如把“这段时间流过多少”当成“速度”）；拿到数字不和常识/参照值比一比
- 作业跑着的时候改测量代码并部署
- 失败的作业在共享节点 `/tmp` 留下垃圾
- 把后台传输挂在交互会话里
- 用户改了条件，只改文档不停作业，或者只停作业不记决定

## 交付前检查

- [ ] 设计文档写明固定条件、改动及理由、有效点标准、停测规则、可疑判定
- [ ] 本地单元测试全过；冒烟测试只跑了一个点，所有记录文件都在，现场已清理
- [ ] 每个作业的 `run.json` 有源码提交号（非 dirty）、配置哈希、硬件身份
- [ ] 看门狗两层都在跑，状态板能打开
- [ ] 用户已经说了“开跑”，并拿到了查看状态的命令
- [ ] 提交后本轮没有设置任何定时唤醒或轮询
