# 固定 Git 协作流程

本流程是跨任务一致的仓库协作约定；模型与调度方式可以替换，提交继承与主代理merge规则保持一致。项目只需确定整合主分支名（例如main或experiment）、远程名及承担主代理职责的协调者。仅本地模式同样适用，省略fetch/push；人类/设备的交付可由指定录入者按此流程提交。

## 1. 子代理从主分支提交派生

开始工作前读取任务单中的整合主分支。双仓库模式先fetch该分支，将最新远端主分支的完整SHA记为BASE_SHA；仅本地模式读取本地主分支的SHA。不得把过期缓存当作最新远端。新建独立topic分支及worktree，起点为BASE_SHA；不能从其他子代理未整合的分支随意派生，也不能直接在主分支提交或推送。

存在其他人的未提交改动时保留原工作树，使用独立worktree。每项交付形成独立commit；报告源码身份记录实际实验运行的版本，不能用分支起点或报告提交版本替代。

## 2. 提交前同步并冻结移交

提交前重新读取最新主分支；双仓库模式先fetch。要求当前主分支提交是topic提交的祖先，可用 `git merge-base --is-ancestor TARGET_SHA SOURCE_SHA` 检查。目标前进且尚未被topic包含时，在topic中执行git merge整合最新主分支，解决冲突并重做受影响检查，然后重新移交。

移交包含BASE_SHA、完整SOURCE_SHA与TARGET_SHA、topic名、报告/复现入口、检查记录与限制。双仓库模式只push自己的topic并核对远端SHA；不能push主分支。仅本地模式用本地refs交接。提交者不得自行批准或合并自己的交付。

## 3. 主代理审核冻结版本

主代理或独立审核者审查精确SOURCE_SHA相对TARGET_SHA的diff及受影响完整材料，分别判断交付合规、证据有效性与科学结论。审核记录绑定两个完整SHA、审核者、检查与批准依据。

审核或合并前任一端变化，旧批准不能直接沿用。更新移交、检查祖先关系并重新审核受影响内容；不能用现场最新SHA替换记录来假装旧批准仍有效。主代理自己实施的内容交由其他获授权者审核，主代理身份不等于自批权限。

## 4. 主代理用git merge整合

最终整合只由承担主代理职责且获整合授权的协调者执行。分支名/remote名来自项目配置，批准SHA来自审核记录：

1. 检查工作树干净；重新核对source与target。双仓库模式fetch后核对远端两端均等于批准值。本地主分支须等于批准TARGET_SHA；允许ff-only同步到该值，出现本地分叉则停止处理，不能reset或强推覆盖。
2. 再次检查TARGET_SHA是SOURCE_SHA的祖先。在整合主分支执行 `git merge --no-ff --no-commit APPROVED_SOURCE_SHA`，运行相关整合检查，再提交merge commit。检查失败或发生意外冲突时不提交/推送，保留诊断、恢复合并前状态并退回修订；不能借合并机会添加未经审查的实验改动。
3. 校验merge commit恰有两个父提交，第一父为批准TARGET_SHA，第二父为批准SOURCE_SHA。即使可以fast-forward也保留merge commit；不使用squash、cherry-pick或复制文件代替合并。
4. 双仓库模式普通push主分支并核对远端SHA。若远端前进导致拒绝，重新同步、冻结、审核，不强推。仅本地模式记录本地merge SHA，不能声称已远程同步。

`BASE_SHA`、`TARGET_SHA`等是待替换的记录字段，不是可直接照抄的Git ref。无主分支内容变化的交付无需制造空merge。文本流程不替代平台权限保护；未配置并验证保护规则时不宣称不可绕过。
